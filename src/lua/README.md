# Lua effects on the panel

The scripts in [`tools/luasim/scripts/`](../../tools/luasim/scripts) run on the
panel, each as a page of its own: **MINECRAFT, ROOM RADAR, SNAKE CLOCK, TETRIS
CLOCK**. The knob walks the clock styles, then each effect, then the other
pages; the carousel walks them the same way and gives each its slot. The
banner names an effect however you arrive at it — knob, carousel or web.

Build flag `LUA_EFFECTS_ENABLED`, on in `env:matrix-waveshare-rgb`. It needs
`NSLUA_ENABLED` and `CONTROL_ENCODER_ENABLED` (`#error` otherwise), and
`+<lua/>` in the source filter.

`demo.lua` is not embedded (a test card for the API), nor is `world_clock.lua`:
the world clock is already a native page drawing the same picture, and a
second copy would show twice in the rotation. Both are one line in
`tools/luasim/gen_effects.py` (`SKIP`).

## Files

| | |
|---|---|
| `lua_effects.h` | the four calls the web UI codes against |
| `lua_effects_page.h` | the hooks `main.cpp` calls |
| `lua_effects.cpp` | the task, the frame handover, the blit, the error screen |
| `lua_fx.{h,cpp}` | one effect in one persistent `lua_State`: open, `draw()`, close, budgets, heap cap |
| `lua_px.{h,cpp}` | the `px.*` API, drawing into a 128×64 RGB888 canvas |
| `nslua_sandbox.{h,cpp}` | the whitelist, moved out of `nslua.cpp` unchanged so both runtimes share it |
| `lua_effects_scripts.h` | GENERATED by `tools/luasim/gen_effects.py`; the pre-commit hook runs `--check` |

`lua_fx`, `lua_px` and `nslua_sandbox` have no Arduino dependency: the host
build in `tools/luasim/fx_parity.py` compiles exactly these files.

## Design

**One persistent state per effect.** On the panel a fresh sandboxed state costs
2.54 ms and an allocation-heavy `nslua_run` inline once per frame dropped the
clock to 5 fps (phase 6b bench). So an effect is loaded once when its page
arrives, its global `draw()` is called per frame, and the state is closed
when the page goes, which frees its whole heap.

**The canvas is ours, not the panel's.** The DMA panel has no readable
framebuffer, and `px.get`, `px.blend` and `px.glow` read before they write.
`px.*` draws into a 128×64 RGB888 array in PSRAM, and the render copies it to
the panel with `drawPixelRGB888`, every pixel, once per frame.

**Threading: a task on core 0, a blit on core 1.** The alternative — `draw()`
in the render path at a capped rate — was rejected on three measured grounds:

1. *Cost.* `room_radar` runs 304 000 instructions a frame (exact, host). At the
   panel's measured 410 ns per instruction (the bench's `kCompute`: 64.1 ms
   less 2.54 ms for the state, over 150 000 instructions) that is about 125 ms
   of VM time per frame before any pixel work — `loop()`, the web server and
   MQTT would stand still for it every frame.
2. *Isolation.* The same bench ran Lua flat out in a task on core 0 and the
   clock's render on core 1 lost only 0.3–0.7 ms a frame.
3. *Stack.* `loopTask` has 8 KB (`CONFIG_ARDUINO_LOOP_STACK_SIZE`), shared with
   everything `loop()` calls.

The task is `luafx`, priority 1, pinned to core 0 with Wi-Fi. It draws at up to
the effect's `FPS` and always sleeps at least a tick between frames, because
IDLE0 is watched by the task watchdog (`CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU0`).
When no render has asked for a frame for 1.5 s — display scheduled off — it
stops drawing.

**Handover.** Four PSRAM buffers: `work` (the canvas; it persists between
frames, as luasim's does), `spare` and `ready` on the task's side, `front` on
the render's. After `draw()` the task copies `work` to `spare` and swaps
`spare` with `ready`; the render swaps `ready` with `front` and blits `front`.
A spinlock guards only the pointer swaps. Each selection is numbered and every
frame and error carries its number, so leaving a page and coming back is a
fresh start — a failed effect is retried — and nothing from an earlier visit is
shown. The render rate is the effect's `FPS`, lowered to the rate frames are
actually arriving, so a slow effect is not blitted three times per frame. The
Lua page skips the frame clear: the blit writes every pixel, and a clear would
only flash black.

**The stack is internal RAM, 16 KB.** The Watch put its Lua task's stack in
PSRAM; that does not carry over. It runs IDF 5.x; arduino-esp32 2.0.17 is built
with `CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY` unset (`tools/sdk/esp32s3/sdkconfig`),
and in its `libfreertos.a` `xTaskCreateStaticPinnedToCore` asserts
`xPortcheckValidStackMem`, which only calls the internal-memory TCB check.
16 KB rather than the bench's 32 KB because the scripts are compiled in, never
uploaded, so the parser never meets a hostile nesting depth; on the host they
used under 3 KB above the harness. If scripts ever arrive at run time, go back
to 32 KB and measure the internal heap first.

## What a script sees

- `px.*` exactly as luasim, held to it pixel for pixel (below). The only
  departures bound C work off the canvas, which the instruction hook cannot
  see: huge lines are clipped (may land a pixel off), circles with a radius
  over 16 384 are skipped; the rest are clipping that cannot change a pixel.
- `px.t()` is the wall clock's phase over `PERIOD` seconds (a script global,
  default 60), aligned to the epoch: at 60 it is the second hand, so
  `tetris_clock` and `snake_clock` finish building the next time as it arrives.
  `room_radar` sets `PERIOD = STORY`, its 24 s scene. `px.t()` and `px.now()`
  come from one clock reading per frame.
- `px.now()` is local time, 0-based `yday`, and `utc` in hours (an integer for
  whole-hour zones, as in luasim; 5.5 for India).
- The nslua whitelist: `base`, `table`, `string`, `math`; no `load`, `dofile`,
  `loadfile`, `collectgarbage`; `print` and `log` go to serial. No `coroutine`
  (a new thread would start with a fresh hook count), no `sys`.
- Generational GC: on the shipped scripts it matched the incremental collector's
  draw time and never peaked higher.

## Budgets

Set in `kLuaFxPanelLimits` (`lua_fx.h`). From four scripts, so these are
reference values with headroom, not limits derived from a distribution:

| | Limit | Heaviest shipped script (exact, host) | Basis |
|---|---|---|---|
| load | 20 000 000 instr, 3 s | room_radar 1 021 325 (≈420 ms on the panel at 410 ns) | its fan grid is precomputed once |
| one `draw()` | 2 000 000 instr, 500 ms | room_radar 310 217 max (≈127 ms VM) | 2 M is `NSLUA_INSTR_BUDGET`; 500 ms is ~4× the estimate |
| heap | 4 MB PSRAM | room_radar 118 KB peak | 16 MB PSRAM, almost all free |

A syntax error, a runtime error, either budget or the heap cap stops the
effect: the panel shows `LUA ERROR`, the effect's name and the first line of
the message; serial gets the traceback. Choosing the page again retries.

## Checked

`python3 tools/luasim/fx_parity.py` compiles `lua_fx.cpp`, `lua_px.cpp` and
`nslua_sandbox.cpp` for the Mac against a stand-in display, drives them with
luasim's clock, and compares raw frames byte for byte — after a negative
control proves it can see a one-minute difference. All six scripts, at 12:34
over 240 frames, across 23:59, over a whole-day sweep, and at 06:10 on 1 January
in UTC−5: **identical, every frame**, under the panel's budgets.

| script | draw instr avg / max | host ms avg / max | heap peak | panel VM estimate |
|---|---|---|---|---|
| minecraft | 13 361 / 13 902 | 0.049 / 0.082 | 44 KB | 5.5 ms |
| room_radar | 303 985 / 310 217 | 0.95 / 1.04 | 118 KB | 125 ms |
| snake_clock | 6 758 / 28 160 | 0.031 / 0.151 | 90 KB | 2.8 / 11.6 ms |
| tetris_clock | 8 320 / 31 631 | 0.032 / 0.277 | 111 KB | 3.4 / 13.0 ms |

The panel estimates are VM time only, from the bench's rate; `px.*` pixel work
comes on top. Nothing here has run on the panel yet.

## Cost

Against the same env at `bb55814`: **+48 832 B flash** (34 190 B of it the
four embedded scripts' source), **+480 B static RAM**. At run time: 16 KB of internal heap
for the task's stack, 4 × 24 576 B of PSRAM for the buffers, and the effect's
Lua heap in PSRAM while its page is up.

## To measure on the panel

The task prints what to read:

- `[luafx] N effects, task on core 0 with 16384 B stack (internal free A -> B)` at boot.
- `[luafx] open <id>: ok in X ms, ~I instr, heap H B, ... stack free S B` per visit.
- Every 30 s on an effect: frames and fps achieved, draw avg/max ms, heap and
  peak, stack free, PSRAM free, internal heap free and minimum.

What those should answer: each effect's real frame time and fps (room_radar is
the one at risk); whether the full-panel blit tears or flickers at the DMA's
84 Hz — if it does, `display.waitForScanCompletion()` before the blit is the
first thing to try; the internal heap minimum with the 16 KB stack taken;
the stack high-water mark; and that PSRAM returns to its start value after
leaving an effect.

## Honest limits

- Before NTP sync `px.now()` reads 1970: the clock effects draw a wrong time
  rather than refusing, unlike the native world clock.
- The panel estimates above are from one bench number, not from these scripts
  on the panel.
